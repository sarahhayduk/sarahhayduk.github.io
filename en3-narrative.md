# Enhancement Three Narrative
## Databases: Reverse-Engineered Client Service Management System (SQLite/C++)

The Reverse-Engineered Client Service Management System originates from CS-410 Software Reverse Engineering. The original artifact was a single-file C++ program that stored all client names, service selections, and the authentication password directly in the source code. Although I had previously refactored the program to use a vector of structured client objects in place of global variables, the underlying vulnerability remained: reverse engineering tools could still extract all sensitive information from the compiled binary. This made the artifact ideal for the Databases category, since it lacked any form of secure external data storage and provided a clear opportunity to demonstrate secure data handling practices.
	
For this enhancement, I redesigned the program to use SQLite as a persistent, externalized data store. I incorporated SQLite’s amalgamation files to embed the database engine directly into the project and created a schema with Clients and Users tables. All hardcoded client information and the system password were moved into an external **seed.sql** file that executes only when the database is first created. This ensured that no sensitive strings appear in the executable, directly mitigating the reverse‑engineering vulnerability. I also expanded the program’s functionality by adding the ability to insert new clients at runtime and by loading all client data dynamically from the database. The final design separates data and logic into dedicated files, which improves maintainability and aligns with modern software engineering practices.
	
As part of this structural improvement, and in collaboration with instructor feedback, I separated all menu-related functionality into a dedicated Menu module. This keeps the main program focused solely on initialization, authentication, and high-level control flow, resulting in a cleaner and more maintainable architecture. I also incorporated secure error-handling practices by routing all database-tier failures to an internal diagnostics log file. This prevents SQLite error messages, schema details, and other sensitive internal information from being exposed to the user interface, strengthening the system against information disclosure weaknesses.
	
To further improve stability and resource safety, I wrapped all raw **sqlite_stmt\*** pointers in RAII smart-pointer wrappers equipped with **sqlite3_finalize** as a custom deleter. This ensures deterministic cleanup of prepared statements even when early returns or unexpected runtime interruptions occur. This enhancement eliminates the risk of raw SQLite statement leaks and reflects modern C++ memory-management practices.
	
Building on this security-focused redesign, I further strengthened the system by replacing the plain-text password storage model with salted cryptographic hashing. While moving the credential into seed.sql removed it from the compiled binary, the password still existed in readable form within the resulting SQLite database. To address this, I redesigned the authentication system to use **Argon2id**, implemented through the **Monocypher** cryptographic library. Monocypher is a lightweight, self-contained C library that can be included directly as source files, which keeps the build process consistent with how the SQLite amalgamation is integrated. This avoids external dependencies while still providing a modern, memory-hard password-hashing algorithm. The system password is now combined with a unique 16-byte salt and transformed into a 32-byte Argon2id hash. Only the hash and salt are stored in the Users table, and user input is verified at runtime by re-hashing the provided password with the stored salt and comparing the results. This portion of the enhancement demonstrates a deeper security mindset by ensuring that credentials remain protected even if the database file or seed script are accessed directly.
	
The process of enhancing this artifact taught me several important lessons about toolchains, modularization, and secure data design. During development, I discovered that the Codio Eclipse environment only supported up to the C++1y language standard, which predates the full introduction of the **\<filesystem\>** library. Because my enhanced design relied on C++17 features to manage database file paths and initialization, the Codio compiler was unable to build the project. To resolve this, I pivoted from my proposed plan and used my local Visual Studio environment, which provides full C++17 support. This decision reflects real-world engineering practice, where toolchain limitations must be evaluated and the development environment adjusted to meet project requirements.

One of the more subtle debugging challenges I encountered involved the Client struct. Because the original artifact stored all logic in a single monolithic file, the struct definition existed directly inside the main source file. After refactoring the program into a modular design with a dedicated **Database.h** header, I overlooked that the original struct definition was still present in the main file. This resulted in two competing definitions of Client, which caused misleading compiler errors that pointed to unrelated lines of code. The issue was not immediately obvious because the compiler did not explicitly report a redefinition; instead, it produced cascading type-related errors. Once I traced the problem back to the duplicate struct, removing the redundant definition resolved the issue and returned the project to a stable build state. This debugging process reinforced the importance of carefully managing data structures during modularization and highlighted how structural refactoring can introduce subtle, non-syntactic errors. Overall, this enhancement strengthened my understanding of secure data design, database integration, and the importance of selecting the right tools for the job. It also demonstrated how reverse engineering principles can guide defensive programming decisions. By transforming a vulnerable, hardcoded program into a secure, database-backed system with Argon2id-based authentication, I gained valuable experience in both software architecture and secure development practices.

This enhancement fully meets the course outcomes I selected in Module One. For Outcome 4, the integration of SQLite with prepared statements, the use of C++17 features, the introduction of RAII based resource management, and the transition to a modular architecture demonstrate my ability to apply well founded tools and techniques to deliver a more secure and scalable solution. For Outcome 5, removing all sensitive information from the binary, implementing cryptographic password hashing, and designing a system that anticipates reverse engineering and information disclosure threats directly supports the development of a security mindset. The enhanced artifact now protects client data, externalizes credentials, and ensures that neither the compiled program nor the database exposes private information through static analysis or unauthorized access.
